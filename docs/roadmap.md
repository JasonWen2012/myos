# myos 路线图：七个阶段

这份文档是**计划**，不是已完成的功能清单。当前能做什么看
[`README.md`](../README.md)，已经踩过的坑和内部原理看
[`docs/design.md`](design.md)。

阶段划分来自你给的顺序（地基 → 进程 → 文件系统 → 设备 → 用户态 → 图形），后来在图形之前补了
一段**脚本语言**（第 8 节），因为"让盘里的文本文件能跑"要靠用户态的文件接口和 libc，而图形是
"锦上添花"——两者之间正好放得下一个能独立验收的阶段。下面每个阶段都写清：**目标 / 为什么在这个
位置 / 交付物（具体文件）/ ABI 与格式变化 / 验收（可测断言）/ 依赖 / 非目标 / 风险**。看完这份
文档应该可以直接开工，不需要再决定"先做哪个"。

## 0. 现状基线（2026-02 更新）

已经跑通的部分：

| 层 | 状态 |
|---|---|
| 引导 | 自研两阶段 loader：实模式 → 校验 16 字节自校验头 → 32 位镜像暂存 0x10000 后进保护模式搬到 1 MiB |
| 16 位内核 | 实模式、直写显存的控制台、键盘（INT 16h）、shell；用自研模拟器验收 |
| 32 位内核 | C++，自己的 GDT/IDT/PIC/PIT、IRQ1 键盘、IRQ4 串口、VGA+COM1 双输出控制台、`kprintf`、分页/物理分配/内核堆、ring3 + `int 0x80` syscall、**任务表 + 抢占式轮转调度**、自检 68 项（内存 14 + 特权级 15 + 文件系统 13 + 调度 11 + 基础 15） |
| 存储 | 自己的 ATA PIO 驱动（轮询）、MBR 分区解析、**myfs** 文件系统：读写、`fsck`、跨启动持久化 |
| 工具 | 自研 PE32 链接器 `tools/cofllink.py`（内核/loader/用户程序三套布局）、主机侧文件系统实现 `tools/myfs.py`、QEMU 测试后端 |
| 测试 | 238 个用例（7 个模块）全绿；32 位用 QEMU 真固件验收，没装 QEMU 就 skip |

写新代码前必须知道的几个"当前事实"（都会限制设计）：

| 事实 | 位置 | 对后续阶段的影响 |
|---|---|---|
| GDT 已是 6 项：null / ring0 code+data / **ring3 code+data / TSS** | `kernel32/gdt.cpp` | 用户态的段与 TSS 已就位；第二阶段只需给每个任务换 `esp0` |
| IDT 有通用的 `idt_set_gate(vector, handler, selector, flags)`，`int 0x80` 已做成 **DPL3 门（0xEE）** | `kernel32/idt.h` / `idt.cpp` | syscall 入口已通；信号、缺页投递沿用同一形状 |
| 中断桩的帧形状固定（`gs fs es ds \| pushad \| vector error \| eip cs eflags`） | `kernel32/isr.asm` | syscall/缺页/信号都要沿用这个形状，不要另发明一套 |
| PIC 只放行 IRQ0/1/4，从片整块屏蔽 | `kernel32/pic.cpp` | 第四阶段要接更多 IRQ；ATA 现在是轮询，没接 IRQ14 |
| 打开文件表是**全局的 8 槽**，而且只读（open/read/close） | `kernel32/file.h` | 第三阶段要改成每进程 fd 表 + 写/定位 |
| **分页 + 物理分配器 + 内核堆 + ring3/syscall/usercopy + 任务/调度都已经有了**（第一阶段 1a/1b、第二阶段 2a，见 3.1/3.2/4.1）；页目录现在**每任务一份**（页表仍共享） | `kernel32/pmm.h` / `paging.h` / `heap.h` / `user.h` / `task.h` | 2b 的 `fork` COW、用户半区、用户态堆都建在它上面 |
| **没有 RTC**，唯一的时间概念是 100 Hz tick 计数 | `kernel32/pit.h` | 时间戳、`clock_gettime`、`sleep` 精度都要它（第四阶段） |
| myfs v1：inode 32 字节只有 类型/大小/12 个块号，**没有 link count、mtime、mode、父指针** | `kernel32/fs.h` + `tools/myfs.py` | 第三阶段的硬链接/时间戳要升到 v2 |
| loader 只能把镜像暂存在 `0x10000..0x80000`（448 KiB = 896 扇区），因为实模式写不到 1 MiB 以上 | `boot/boot.inc` | 内核现在 **224 扇区**，还有余量；超过阈值要改造 loader（见风险表） |
| QEMU 测试用 `-m 32` | `tools/qemu.py` | 多进程 + 页表会不够，计划提到 64 MiB（**2b 开工前做**） |
| `ld` 产不出裸机镜像 → 用户程序也得用自研链接器 | `tools/cofllink.py` | `user_layout()` 已完成，第二阶段的新程序照抄 `USER_PROGRAMS` 的模式 |
| 任务表是**定长 16 槽**，任务是纯内核任务，**没有用户半区、没有睡眠队列、没有空闲任务** | `kernel32/task.h` / `sched.h` | 2b 要让用户程序成为任务并加 `hlt` 空闲任务；3 个用户进程的验收要求先把槽位和 `-m` 调好 |
| 全内核**没有锁**（单 CPU、切换只发生在明确定义的点上） | `kernel32/sched.cpp` | 2b 起要明确规定"哪些操作不能被抢占"（现在只有 `sched_pause()` 一段） |

## 1. 对这份划分的评估（含后加的"脚本语言"一段）

**总体结论：顺序是对的**，和真实操作系统教科书的推进顺序一致——先把地址空间和特权级立起来，
再让进程跑起来，再让文件系统成型，再补设备和用户态体验，**然后让盘里的文本文件能跑**，最后做
图形。逐条评估与建议调整：

**① "内存管理" 放在最前面：完全正确，而且必须有。** 没有分页就没有用户地址空间、没有
`fork` 的 COW、没有 `mmap`、没有崩溃隔离；没有物理分配器就没有 `fork`。唯一要分清的是
内部顺序：**先物理分配器 + 页表 + 缺页，再按需零页**，这三件事有严格依赖。

**② COW 建议挪到第二阶段的 `fork`。** COW 的语义是"两个地址空间共享一页，谁写谁复制"，
没有两个进程的时候只能人工造两个映射来演示，验不出真问题。第一阶段只留"页表项支持只读
共享 + 一个 `copy_page()` 原语"，真正的测试放在 `fork` 落地时（父子写同一页互不影响、
页帧引用计数回到起点）。

**③ "用户态/内核态分离 + syscall 入口" 建议明确拆成 1a/1b 两个里程碑。** 它依赖分页
（ring3 代码得先被映射）和 TSS（ring3 中断进来要换栈），而且它自己需要一个**能被启动的
用户程序**才算完成——否则"syscall 能用"无法证明。所以第一阶段的验收是"一个 ring3 程序
打印一行、`exit` 回到内核 shell"。

**④ "工程化" 里建议补三件你列表里没写、但会拦住后面的东西：**
- **用户镜像格式与加载**：本机 `ld` 产不出裸机镜像，所以用户程序要复用 `cofllink`（新
  `user_layout()`）+ 16 字节 MYOS 头，由内核从 myfs 卷里读出来映射到用户地址。这件事
  定不下来，第二阶段就没法启动任何用户程序。
- **`copy_from_user` / `copy_to_user` 纪律**：所有 syscall 参数必须逐页校验。没有它，
  "用户态/内核态分离"只是把代码分了两块，用户程序仍能读写内核内存。
- **RTC / 时钟源**：现在只有 tick 计数。文件时间戳、`sleep`、`clock_gettime` 都要它。

**⑤ tty 建议提前到第二阶段（最小版）。** 你的第四阶段才做"终端"，但第二阶段的进程要能
读写终端、Ctrl-C 要能投递给前台进程组——那是终端驱动的职责。建议：**第二阶段做最小 tty
（行规程：回显、退格、行缓冲、Ctrl-C 转 SIGINT）**，第四阶段再把它升级成正式驱动
（可配置模式、`ioctl`、作业控制）。

**⑥ 第 3–6 阶段的顺序合理**，只补一点：跨设备 `mv` 需要第二块设备，所以第三阶段要顺手
加一个 **ramdisk/tmpfs 设备**，否则"跨设备移动"没法测。

**⑦ 缺的整块内容**（已补进第 10 节）：`docs/abi.md` 冻结 syscall 表、用户程序构建流程、
每阶段的自动验收、内核镜像预算看门狗。

**⑧ "让盘里的脚本能跑"（后加的第 8 节）放在用户态之后、图形之前。** 现在 `/bin` 里放的是
**构建时编译好的扁平机器码镜像**（`MYOS` 头 + arch 3），内核对"程序"的定义就这么窄：把
`hello.py` 放进卷里，`run` 只会说 `invalid argument`。要让它能跑，有两条完全不同的路：

- **脚本解释器**（这一节做的）：语法是 Python 的**子集**，由 myos 自己解释。真正的位置在
  第五阶段之后——用户态解释器要能自己 `open`/`read` 脚本（第三阶段的 VFS）、要有用户堆
  和 libc（第五阶段）。这也正是它排在图形之前的原因：它依赖前面全部，而不被任何人依赖。
- **真正的 C/C++ 编译器**（放进"可能会做"一节）：chibicc/tinycc 量级（1 万–3 万行），要它
  自己的 libc 和写文件的能力，是整条路线图里最大的一块，所以只作为**可选的大里程碑**列在
  第 11 节，不占阶段号。

**为什么中间那条路（内核里塞一个解释器）不单独占一个阶段**：草稿证明它几十行就能跑起来，但
在内核里解释不可信文本是把攻击面放进了最该干净的地方；而且它没有 `open`/`read` 就只能靠
内核替它读文件，等于把"程序读自己的数据"这件事一直留在内核里。放在第五阶段之后，解释器是
一个普通用户程序，和内核隔离，还能继续长大（字节码、更多语法）。设计决策已经在第 8 节全部
写下来（子集、上限、分派规则、验收），所以那一段并不是"以后再说"，而是"轮到它就能直接开工"。

## 3. 第一阶段：打地基

**总目标**：内核第一次拥有"地址空间"和"特权级"这两个概念。

### 3.1 里程碑 1a：内存管理（**已完成**）

| 项 | 内容 |
|---|---|
| **目标** | 物理内存分配器 + 页表 + 内核堆 + 能恢复的缺页处理 |
| **为什么在这** | 后面所有东西（fork、mmap、用户地址空间、共享内存）都建立在这三件东西上 |
| **依赖** | 已有：E820 内存图（loader 在 0x6000 给了规范化 24 字节表）、`mem.cpp` 的读取封装 |
| **非目标** | COW（留给第二阶段的 `fork`）、页置换/换出、大页、`mmap` 系统调用、内存映射文件 |

**已经落地的东西**（原理与踩坑见
[`docs/design.md`](design.md#里程碑-d内存管理路线图第一阶段-1a已完成)）：

- `kernel32/pmm.cpp`：4 KiB 页位图分配器，从 E820 可用区间建表；只管理 1 MiB 以上；位图覆盖
  128 MiB，超出的内存计入 `ignored` 并**报告**，不假装有。
- `kernel32/paging.cpp`：二级页表 + identity map + 开 `CR0.PG`/`CR0.WP`；`page_map`/
  `page_unmap`/`page_translate`/`page_flags`/`page_tlb_flush`；`paging_reserve_lazy()` 与缺页
  钩子（按需零页）。
- `kernel32/heap.cpp`：1 MiB 连续竞技场、首次适配、分割与合并、每块 16 字节自校验头。
- `kernel32/panic.cpp` + `idt.cpp` 的 14 号向量分支：能恢复就重试指令，不能就打印 CR2、
  错误码（present/write/user）、寄存器和 EIP，并以失败状态结束运行。
- 命令：`vm`（PMM/页表/identity map/堆，`vm fault` 故意踩未映射地址）、`check`（跑自检但不
  退出会话，可以重复跑）。
- 工具：`python memmap.py --memory` 打印这一层的配置（常量从头文件解析出来，不是抄一遍）。

**验收（已完成：14 条内存自检 + 2 个测试类）**

1. 分配器来回：64 页互不相同、页对齐、不来自低 1 MiB 或内核镜像；全部归还后空闲数回到起点。
2. `page_translate()` 证明内核镜像与显存是 identity map；`read_cr3()` 等于内核建立的页目录。
3. 在新虚拟地址映射一页并写读通过；解映射后 `translate` 回 0。
4. 堆：两块写满互不干扰、全部释放后 `used == 0`、超过整个竞技场的请求被拒。
5. 按需零页：未触碰的页第一次读触发缺页、被映射、重试后读到 0，缺页计数 +1；**同一会话里
   再跑一遍检查仍然全过**（`check` 命令存在的理由之一）。
6. **故障路径**：`vm fault` 写未映射地址 → 串口出现 `cr2 DEADB000 (not present, write,
   kernel)` 与 `KERNEL PANIC: page fault`，进程以失败码退出，QEMU `-d int` 日志里是 `v=0e`
   而**不是** triple fault。

**这一阶段特意留下的**：COW 的页表原语（只读共享 + 引用计数）随第二阶段的 `fork` 一起做；
用户可见的内存接口（`brk`/`mmap`）等 1b 有 ring3 之后再加。

### 3.2 里程碑 1b：工程化（ring3 / syscall / 错误码 / 调试基建）（**已完成**）

| 项 | 内容 |
|---|---|
| **目标** | 一个 ring3 程序能跑起来、通过 `int 0x80` 调内核、`exit` 回到 shell |
| **为什么在这** | 它是"特权级"的验收；并且它是后面 fork/exec 的前提 |
| **依赖** | 1a 的分页（ring3 代码要映射）+ TSS（ring3 异常要换栈） |
| **非目标** | 多任务/调度（第二阶段）、用户态 libc（第五阶段，这里只给最小 syscall 桩） |

**已经落地的东西**（原理与踩坑见
[`docs/design.md`](design.md#里程碑-e特权级与系统调用路线图第一阶段-1b已完成)）：

- `kernel32/gdt.cpp`：GDT 扩到 6 项——null、ring0 code/data、**ring3 code/data（DPL 3）**、
  **TSS**（type 9，`iomap_base` 指向结构末尾 = 没有 I/O 位图，ring 3 一条 `in`/`out` 都用不了）。
- `kernel32/tss.cpp/.h`：TSS 结构（104 字节）+ `esp0/ss0`；每次 `run` 会换成一段专属的
  16 KiB 内核栈（把 shell 自己的栈交给 TSS 会让系统调用帧压在 shell 的局部变量上），
  跑完再还回启动时的栈（`esp0 = 0` 是不行的：下一次 ring3 陷阱会把帧压到地址 0）。
- `kernel32/ring3.asm`：`int 0x80` 桩（沿用现有帧形状，进内核态后换成内核数据段）、
  `run_user_image(entry, stack)`（保存内核栈和 callee-saved 寄存器后 `iret` 进 ring 3）、
  `return_to_kernel(code)`（恢复栈和寄存器，把退出码放在 `eax` 里回到 `exec_user`）。
- `kernel32/syscall.cpp/.h` + **`docs/abi.md`（新）**：调用号/寄存器/错误码/地址窗口/镜像格式。
  v1 实现了 `exit`、`write`（只允许 fd 1/2）、`getpid`（占位 1）、`yield`（占位 0）。
- `kernel32/usercopy.cpp/.h`：`user_range_ok`（逐页检查 present + user）、
  `copy_from_user` / `copy_to_user` / `user_string_ok`；错误码占用 -32..-39 的独立区间
  （和文件系统的 -1..-16 分开，避免"同一个数字两个意思"）。
- `kernel32/user.cpp`：`exec_user(path)`——读卷里的镜像、校验 16 字节头、映射用户页（先清零）、
  映射栈、进 ring 3、等退出、回收所有页。
- `kernel32/panic.cpp` + `klog.cpp`：统一停机报告，以及 `dmesg` 能看的环形日志。
- 用户程序：`user/hello.asm`（手写 ABI）、`user/badwrite.asm`（请求读内核内存）、
  `user/hello.cpp`（编译器生成的调用）——都由 `build.py` 编译、链接、打进 `/bin`。

**验收（已完成：15 条自检 + 11 条测试）**

1. `run /bin/hello` → 串口出现 `hello from ring 3` → 回到 `myos>`（ring3 → `int 0x80` →
   `exit` → 回到内核 shell 整条路通了），报告 2 个系统调用。
2. 自检新增：GDT 里 ring3 描述符的 DPL 是 3（掩掉 CPU 自己会置的 accessed 位）、TSS 已 `ltr`、
   `int 0x80` 门的 DPL 是 3 而其它门都是 0、用户页带 user 位而内核页不带。
3. **越权测试**：`run /bin/badwrite` 让 `write` 去读 `0x00100000`（内核镜像）→ 退出码 **37**
   （E_FAULT），而且串口里**没有**出现内核镜像开头的 `MYOS` 四个字母。
4. 头部校验：把 `/bin/hello` 的校验和字节翻一位，内核报 `invalid argument` 拒绝运行；
   **同一份损坏还被 manifest 校验独立发现**（自检据此以失败码结束，测试明确断言这一点）。
5. `dmesg` 能看到启动里程碑和每一次"entering ring 3 / back from ring 3"。

**估计规模（实际）**：1a ≈ 1400 行，1b ≈ 1300 行，测试 +600 行。

## 4. 第二阶段：进程与调度 + IPC

| 项 | 内容 |
|---|---|
| **目标** | 多个进程能并发运行、能创建/退出/等待、能互相通信 |
| **为什么在这** | 地址空间和特权级有了之后，进程是下一个抽象；文件系统的"每进程 fd"也依赖它 |
| **依赖** | 1a 分页（每进程页目录）、1b ring3/syscall、TSS 每任务栈 |
| **非目标** | 抢占式实时保证、线程（先只有进程）、`clone` 语义、调度公平性度量 |

### 4.1 里程碑 2a：任务与抢占式调度（**已完成**）

**已经落地的东西**（原理与踩坑见
[`docs/design.md`](design.md#里程碑-f任务与调度路线图第二阶段-2a已完成)）：

- `kernel32/task.cpp/.h`：16 槽的 `Task` 表（pid、父 pid、状态 `new/ready/running/zombie`、
  8 KiB 内核栈 + 栈底 canary、**自己的页目录**、ticks、被切入次数、退出码）；
  `task_create_kernel`（造栈帧，让新任务从一次它没调用过的函数返回开始）/ `task_exit` /
  `task_join`（有界的等待）/ `task_reap`（回收栈，只在任务上下文里调用）。
- `kernel32/switch.asm`：`switch_to(save_esp, next_esp)`——只有这件事必须用汇编。
- `kernel32/sched.cpp/.h`：扫表的轮转（不用队列）、`schedule()` / `sched_yield()` /
  `sched_tick()`（由 PIT 每秒 100 次调用）、`sched_pause()/sched_resume()`；切换顺序是
  **先 TSS esp0 和 CR3，再告诉任务层，最后换栈**。
- `kernel32/paging.cpp`（改）：`paging_active_directory()` / `paging_clone_directory()` /
  `paging_switch_directory()`——每任务一份页目录，**页表共享**，所以换 CR3 不会把内核
  从自己脚下抽走。
- 命令：`ps`（任务表）、`schedtest`（建两个**从不主动让出 CPU** 的任务，让定时器抢占，再回收）。
- `idt.cpp`（改）：**EOI 移到处理函数之前**——定时器处理函数会切换任务，而 8259 在服务中
  寄存器被清掉前不会再送同一条线；EOI 放后面等于"时钟在第一次切换后就停住"。

**验收（已完成：11 条自检 + 8 条 QEMU 测试）**：任务 0 就是启动上下文；新任务有独立 pid 与
独立页目录；内核栈有 canary 且不能被写穿；退出码能回到创建者；**中断标志（IF）跟着上下文
走**；**每个任务都被定时器计过 tick** 且都被切入过；回收后堆回到起点；TSS 的 esp0 与 CR3
指向正在跑的那个任务。

**这一阶段特意留下的**：用户程序还不是任务（`run` 仍是代替调用者同步跑，期间用
`sched_pause()` 挡住抢占）；没有 `fork`/COW、没有信号、没有睡眠队列、没有空闲任务
（`task_exit()` 找不到可运行任务时是 panic，不是 `hlt`）。

### 4.2 里程碑 2b：用户进程、fork 与信号（**下一步**）

- `Task` 长出用户半区：用户页表、用户栈、`fork` 的写时复制（页表项只读共享 + 页帧引用计数）、
  `exec`（读用户镜像、重建地址空间）、`exit`/`wait` 的父子关系与僵尸回收。
- `exec_user()` 从"代替调用者同步跑"改成"建立一个任务"——做完这件事，`exec_user()` 里的
  `sched_pause()` 就可以删掉（它只是因为"用户程序不是任务"才存在）。
- 信号最小集：`signal/kill`，`SIGTERM/SIGKILL/SIGCHLD/SIGINT`，在"返回用户态"边界投递；
  `SIGCHLD` 配合 `wait`；进程组/会话（`setpgid`/`setsid`/`tcsetpgrp`）的记账。
- 睡眠队列 + 空闲任务（`hlt`），让"等待"不再靠空转 `sched_yield()`。

**验收**：`schedtest` 起 3 个用户进程交替打印，`ps` 显示它们都拿到过 CPU 时间；
**COW**（父子各写同一地址 → 双方读回自己的值，结束后页帧空闲数回到 fork 前）；
`kill` 一个死循环用户程序 → 它消失、`wait` 收到退出状态；Ctrl-C 送到前台进程组。

### 4.3 里程碑 2c：IPC 与最小 tty

- IPC：`pipe()`（环形缓冲 + 读写阻塞/唤醒）、共享内存最小集（`shm_map(name)` / `shm_unmap`，
  两个地址空间映射同一物理页）。
- **最小 tty（提前到这里）**：`kernel32/tty.cpp/.h`——输入队列 + 规范模式行规程
  （回显、退格、行缓冲、Ctrl-C → 给前台进程组发 `SIGINT`），键盘/串口作为它的输入源；
  内核里的旧 shell 改成"通过 tty 读行"的普通用户程序（或者先并行保留）。

**验收**：管道传 1 MiB 伪随机数据、接收端校验和一致；共享内存两个进程互相看到对方的修改、
`shm_unmap` 后物理页回收；Ctrl-C 只影响前台进程组，内核 shell 不受影响。

**估计规模**：2a ≈ 900 行（已完成），2b ≈ 900 行，2c ≈ 600 行；测试 +400 行。
**风险**：抢占点正确性（中断返回路径上切换——2a 已经踩过 EOI 和 `esp` 未填完这两个坑）、
fd 表从全局改成每进程（与第三阶段联动）、`-m 64` 下多进程页表的物理页开销。

## 5. 第三阶段：文件系统成型（VFS）

| 项 | 内容 |
|---|---|
| **目标** | 从"myfs 专用代码"变成"VFS + 文件系统实现"，并补上链接、跨设备、元数据 |
| **为什么在这** | 每进程 fd/cwd 需要进程已存在；多设备需要设备模型的前置件（第三阶段先做 ramdisk） |
| **依赖** | 第二阶段的每进程 fd 与任务结构 |
| **非目标** | 日志/崩溃一致性（继续用 fsck）、配额、写时复制文件、网络文件系统 |

**交付物**

- `kernel32/vfs.cpp/.h`：`inode_ops` / `file_ops` / `super_ops`（C++ 抽象接口或函数表）、
  `vfs_open/read/write/close/seek/stat/mkdir/unlink/link/rename/readdir`；`mount`/`umount`
  + 挂载点表。
- 每进程上下文：fd 表（`fd -> {file, offset, flags}`）、`cwd`、`root`；
  `open` 路径解析支持 `.` / `..`（**修掉现在"不支持 `..`"**）、相对路径、`/` 语义。
- **myfs v2 格式**：inode 扩展为 link count + `mtime`/`ctime` + `mode` + 父目录号；
  `tools/myfs.py` 与 `kernel32/fs.h/.cpp` 两份实现同步升级，常量交叉校验测试同步更新。
  **决策：不做就地升级**——新卷由构建生成，已有的 `data/myfs-data.img` 由第三阶段新增的
  `python build.py data-disk --rebuild` 重建（会在文档和命令行输出里明确告知会清空）。
- 链接：硬链接（多目录项指向同一 inode，nlink 增减，最后一个删除时才释放块）、
  符号链接（新 inode 类型存目标路径，`readlink`，路径解析时跟随，限制跟随深度防环）。
- `rename`：同设备原子（改目录项），跨设备走"复制 + 删除"（需要第二块设备）。
- 第二块设备：`kernel32/ramdisk.cpp/.h`（内存块设备，实现块设备接口）→ 提供真正的
  跨设备测试场；顺带验证"块设备抽象"在第四阶段之前就站得住。

**验收（可测断言）**

1. `ln /readme.txt /hard.txt` 后两个名字读到同一份内容，`rm` 其中一个另一个还在，
   两个都删掉后空闲块回到起点。
2. `ln -s /readme.txt /soft.txt` 后 `cat /soft.txt` 得到目标内容；`readlink` 打印目标；
   跟随超过上限（比如 8 层）时报错而不是死循环。
3. `mv /copy.txt /mnt/tmp/`（跨设备）后源不存在、目标内容校验和一致、`df` 两块设备都合理。
4. 路径解析：`cd /a/b`、`cd ..`、`cat ../../x`、`cat /a/../b` 都有正确结果（用主机侧
   `tools/myfs.py` 对照同一目录树）。
5. **交叉验证保持**：内核写完卸载后，主机 `myfs.py --image <盘> --partition 1 --check`
   干净，`--list` 与内核 `ls -R` 的树一致。
6. v2 格式：`check()` 干净、`manifest` 校验通过、旧测试镜像重建后全绿。

**估计规模**：≈ 1500 行 + 测试 400 行。**风险**：v2 格式与两份实现同步（用常量交叉校验 +
主机侧 `check()` 兜住）；`..` 依赖 v2 的父目录号。

## 6. 第四阶段：设备与驱动

| 项 | 内容 |
|---|---|
| **目标** | 设备变成"文件"，终端、块设备、时钟都有正式抽象 |
| **为什么在这** | VFS 有了之后，设备文件才挂得进去；作业控制需要真正的 tty |
| **依赖** | 第三阶段 VFS；第二阶段的 tty（这里升级它） |
| **非目标** | PCI 枚举以外的即插即用、DMA 完整框架（先中断 + PIO）、网卡/USB |

**交付物**

- `kernel32/device.cpp/.h`：设备号 + `dev_ops`（open/close/read/write/ioctl）+ 设备注册表；
  `/dev` 目录里出现设备 inode（VFS 的特殊 inode 类型）。
- tty 正式化：`/dev/tty0`（VGA，可读写）、`/dev/ttyS0`（COM1）；行规程可配置
  （规范/原始模式）、`ioctl` 最小集（`TIOCGPGRP`/`TIOCSPGRP`/`TIOCSCTTY` 之类）、
  前台进程组与 `SIGTTIN`/`SIGTTOU`；**作业控制**（`Ctrl-Z`/`fg`/`bg` 需要 `SIGTSTP`
  与 `SIGCONT`）。
- 块设备抽象 + 缓冲缓存：`blockdev` 接口 + `bread/bwrite`（LRU，脏块 + `sync` 落盘、
  命中率统计）；ATA 驱动实现该接口（可选：把轮询改成 IRQ14 中断驱动，作为"中断驱动
  块设备"的练习）。
- 时钟与定时器：`kernel32/rtc.cpp/.h`（CMOS 0x70/0x71 读年月日时分秒，处理 BCD 与
  更新进行中标志）→ `clock_gettime` / `time`；`kernel32/timer.cpp/.h` 软定时器
  （到期回调、`sleep` 用 ms 精度）；tick 与 ms 的换算集中一处。
- 中断体系：按需放行更多 IRQ、共享中断支持、每个 IRQ 的计数（`irqstat` 命令）。

**验收（可测断言）**

1. `ls /dev` 列出 tty/fb/块设备；`cat /dev/ttyS0` 能读到另一端的输入。
2. Ctrl-C 中断前台进程、`Ctrl-Z` 挂起它、`fg` 恢复（作业控制的最小闭环）。
3. 块缓存：重复读同一目录 100 次，命中率 > 90%（`blkcache` 命令报告）；写入后不 `sync`
   立即断电（QEMU 强杀）→ 重启后 `fsck` 能说明丢了什么、且卷不损坏。
4. `date` 打印真实日期时间（与宿主时间误差 < 2 分钟）；`sleep 1` 实测误差 < 5%。
5. IRQ 计数：键盘敲 N 次、IRQ1 计数 +N；串口输入 M 字节、IRQ4 +M（现在只有 IRQ4 有计数）。

**估计规模**：≈ 1200 行 + 测试 300 行。**风险**：中断上下文里使用缓冲缓存/唤醒等待者
（必须明确"中断里可以做什么"）；作业控制的 ABI 细节多。

## 7. 第五阶段：用户态体验（shell + libc）

| 项 | 内容 |
|---|---|
| **目标** | 用户态 libc + 用户态 shell：管道、重定向、`$PATH`、环境变量都能用 |
| **为什么在这** | 需要前面的进程/信号/tty/fd；shell 是所有这些的集成测试 |
| **依赖** | 第二至第四阶段的全部；`docs/abi.md` 里的 syscall 表要冻结 |
| **非目标** | 完整 POSIX（不做 `select`/`poll` 大而全、不做动态链接）、多用户权限语义 |

**交付物**

- 用户态 libc（`user/lib/`）：字符串/内存函数、`printf`/`snprintf`、`malloc/free`
  （基于 `brk` 或 `mmap` syscall）、syscall 桩（每个一行内联汇编）、`errno`、
  启动代码（`_start` → 解析 argc/argv → `main` → `exit`）。
- syscall 补齐：`open/close/read/write/lseek/fstat/mkdir/unlink/dup/dup2/pipe/fork/
  execve/waitpid/getpid/kill/sigaction/brk/chdir/getcwd/exit/time`。
- 用户态 shell（`user/shell/`）：命令表、参数拆分（引号/转义最小集）、
  `>` `>>` `<` 重定向、`|` 管道、`&` 后台、环境变量（`environ`/`getenv`/`setenv`）、
  `PATH` 查找、内建命令（`cd`/`exit`/`export`/`unset`）、`$?` 退出码、Ctrl-C 前台作业。
- 常用小程序（`user/bin/`）：`ls`、`cat`、`wc`、`echo`、`sleep`、`ps`、`kill`、`date`。

**验收（可测断言，尽量用"跨实现"断言）**

1. `ls / | wc` 的输出行数是真实条目数（主机侧用 `myfs.py --list` 数一遍对照）。
2. **`cat /hello.txt > /copy.txt` 之后结束 QEMU，主机侧
   `python tools/myfs.py --image data/myfs-data.img --partition 1 --extract /copy.txt`
   内容与 `files/hello.txt` 完全一致**——端到端跨实现验证（延续现有 manifest 的思路）。
3. `export FOO=bar; echo $FOO` 打印 `bar`；`PATH=/bin; ls` 能在 `/bin` 找到程序。
4. 重定向与管道组合：`cat /readme.txt | wc > /count.txt`，主机侧读回内容正确。
5. `$?`：`false; echo $?` 非 0，`true; echo $?` 为 0。
6. Ctrl-C 终止前台 `sleep 100`，shell 继续可用（回到提示符）。
7. 回归：QEMU 会话里的 kernel shell（第一阶段起就有的那个）仍可用（作为应急入口）。

**估计规模**：≈ 2000 行（其中 libc 800、shell 600、小程序 400）+ 测试 400 行。
**风险**：syscall 表冻结后改动成本；用户态 `malloc` 与内核堆的边界（谁管哪段地址）。

## 8. 第六阶段：脚本语言（图形界面之前）

**目标**：往卷里放一个文本文件，就能跑它。语法是 Python 的子集，由 myos 自己解释。

**为什么在这个位置**：解释器要能**自己读脚本**（第三阶段的 `open`/`read` + 每进程 fd）、要有
用户堆（`brk`/`mmap`）和用户态 libc（第五阶段），所以它排在用户态之后；它又不被任何东西依赖
（图形不需要它），所以正好卡在图形之前。这一节也回答"什么时候能跑盘里的 .py"——**这里**；
而"在 myos 里编译 .cpp"是另一个量级的东西，见第 11 节。

| 项 | 内容 |
|---|---|
| **依赖** | 第三阶段的 VFS（`open`/`read`/`close`、每进程 fd）、第五阶段的用户态 libc 与 shell |
| **非目标** | CPython / MicroPython（要 libc、POSIX、浮点，十万行量级）、浮点数、类与继承、异常、生成器、`import`/标准库、真正的性能 |

### 8a. 语言（Subset，按这个范围实现，多了不做）

| 类别 | 内容 |
|---|---|
| 字面量 | 整数（32 位有符号）、字符串（单双引号）、`True`/`False`（就是 1/0，没有独立的 bool 类型）、列表 `[1, 2, 3]` |
| 变量 | `name = expr`，全局一份作用域（没有函数，所以没有局部作用域） |
| 控制流 | `if`/`elif`/`else`、`while`、`for v in <列表>`、`break`、`continue`、`pass`；**块用缩进**（和 Python 一样，缩进宽度必须自洽） |
| 运算符 | `+ - * / %`（`/` 是**整数除法**，没有浮点）、一元 `-`、比较 `== != < <= > >=`、`and`/`or`/`not`（短路求值）、索引 `a[i]`、字符串拼接/重复、列表拼接 |
| 内置 | `print`（空格分隔、自动换行）、`len`、`range(n)`、`int()`、`str()`、`abs()`，以及列表方法 `.append(x)` |
| 注释 | `#` 到行尾 |

### 8b. 上限（这些是设计，不是暂时限制）

解释器跑的是**不可信文本**，所以每一条上限都是"不能让脚本把机器弄死"：

- 源码 ≤ **8 KiB**（再大就该编译，而不是解释）；每次运行一个 **64 KiB arena**（用完即整体回收，
  没有单次 `free`，也就没有泄漏）。
- 执行节点数 ≤ **200000**（`while True: pass` 会得到 `step limit reached`，而不是把内核转晕）。
- 变量 ≤ 64、列表 ≤ 256 个元素、`range()` ≤ 256、缩进 ≤ 16 层、表达式嵌套 ≤ 24 层。
- 任何错误都是 `line N: 消息` 并返回 shell；**永不 panic、永不重启**。这一条是这一节最重要的
  验收项。

### 8c. 交付物

- `user/bin/py`：用户态解释器（lexer → 递归下降 parser → 树遍历求值器），用第五阶段的 libc
  写；自带的 REPL（不带参数运行进入交互，普通行求值、变量跨行保留）。
- `kernel32/` 里只加**两件小事**：`exec` 的**按内容分派**（`MYOS`+arch3 → 用户镜像；
  `#!` 行或 `.py` 结尾的名字 → 交给 `/bin/py`；其它 → 明确的"这不是程序"），以及给解释器
  配置初始脚本参数的 argv 传递。解释器本身不进内核。
- `docs/scripts.md`（新）：语言参考——上面 8a 的表 + 8b 的上限 + 错误消息，是解释器的合同。
- `scripts/*.py`：仓库里随卷发布的示例脚本（`hello.py`、`fizzbuzz.py`、一个故意报错的），
  和 `files/` 一样进 manifest 校验。
- 可选（同一阶段的第二步）：**字节码 VM**——宿主侧编译器（Python，约 300 行）产出字节码，
  myos 里跑 VM（约 400 行），两边用同一个"两份实现互相校验"的办法（像 `myfs.py` 与
  `fs.cpp`）：宿主反汇编字节码、内核报告执行结果，互相对照。

### 8d. 验收（可测断言）

1. `run /scripts/hello.py` 打印脚本里的内容并回到 shell；`run /scripts/fizzbuzz.py` 输出与
   宿主侧用真 Python 跑同一脚本的结果**逐行相同**（宿主 Python 当参照物，这是这一节最有力的
   断言）。
2. `py /scripts/hello.py` 与 `run` 结果一致；`py`（不带参数）进入 REPL：`x = 1+1` 不报错、
   `print(x)` 打印 2（变量跨行保留）、`exit` 退出。
3. 报错路径：故意写坏的脚本给出 `line N:` 开头的消息、退出码非 0、**shell 仍然可用**；
   `while True: pass` 被步数上限拦住并报告；`1/0`、越界索引、未定义名字各自有明确消息。
4. 分派规则：`run /readme.txt`（没有 `#!`、不叫 `.py`）给出"这不是程序"的说明，而不是去解释
   一个 README；把 `/bin/hello`（机器码镜像）照样按镜像执行，行为不变。
5. 宿主侧：`tools/myfs.py --list` 能看到 `/scripts/*.py`，`--extract` 出来的字节与仓库一致；
   manifest 校验通过（`.py` 文件和别的文件受同一条检查保护）。

**估计规模**：解释器 ≈ 800–1200 行用户态 C++（含 REPL）+ `docs/scripts.md` + 宿主侧对照测试；
可选字节码 VM 再加 ≈ 700 行。

**风险**：用户态 libc 不够用时（`printf` 宽度、`malloc`）会先卡在第五阶段的成熟度上——所以本
阶段的第一条验收就是"能读文件、能打印"；解释器的性能（树遍历）不是目标，脚本长度上限就是为它
准备的。

## 9. 第七阶段：图形界面（锦上添花）

分四小步，每步都能单独停下来。

| 小步 | 目标 | 交付物 | 验收 |
|---|---|---|---|
| **7a TUI** | 文本模式下的面板/窗口库（不切模式，风险最低） | `user/lib/tui/`（框线、面板、滚动区）、`user/bin/top` | QEMU 会话里 `top` 显示多面板界面；按键切换面板（文本断言） |
| **7b 帧缓冲** | loader 里用 VBE 设图形模式并交给内核 | `stage2.asm` 增加 `INT 10h AX=4F00/4F02`（QEMU `-vga std`）+ `boot info` 增加 framebuffer 地址/宽高/stride；`/dev/fb0`；位图字体 + `fill_rect`/`blit` | `screendump` 出 PNG 做**像素断言**（画一个已知颜色的矩形，读回该坐标像素值） |
| **7c 窗口系统** | 用户态客户端 + 事件分发 | 共享内存帧缓冲协议（客户端提交窗口内容）、`user/lib/gui/`、内核/用户态"合成器进程"、焦点与 z-order | 两个窗口叠加正确；点击/按键送到焦点窗口（像素 + 行为断言） |
| **7d 合成器** | 双缓冲 + 脏矩形 | 合成器优化 + `vsync` 概念（QEMU 下用定时器模拟） | 帧率/重绘面积统计：移动一个小窗口只重绘脏区（计数器断言） |

**为什么在这**：它依赖帧缓冲设备（第四阶段）、共享内存（第二阶段）、进程与信号
（第二阶段）、用户态 libc（第五阶段），放最后风险最小。

**非目标**：GPU 加速、OpenGL、字体排版/矢量字体、多显示器。

**风险**：切到图形模式后文本模式控制台就没了 → 需要保存/恢复 VBE 状态，或者保留"双路径"
（内核日志继续走串口，屏幕交给图形）；QEMU 版本对 VBE 模式的支持差异要在
`build.py doctor` 里探测并明确报错。

## 11. 可能会做，目前没打算

- **64 位**（你已明确："目前暂无 64 位打算，以后可能有"）。（可讨论）
- **SMP / 多核**：全程单 CPU，中断与锁按单核假设写（文档里注明）。（可讨论）
- **网络栈**（ARP/IP/UDP/TCP）、**USB**、**PCI 电源管理**。（可讨论）
- **UEFI / GRUB 迁移**：保留自研两阶段 loader 和自研链接器（这是这个项目的性格）。（可讨论）
- **日志式文件系统 / 崩溃一致性**：继续用"写穿 + fsck"（漏块可回收）。（可讨论）
- **多用户与权限模型**：不做 uid/gid 语义与安全边界；inode 里只保留 `mode` 位占位。（可讨论）
- **真机适配**：验收一直以 QEMU 为准（真机只保证"没有依赖 QEMU 特有的东西"）。（可讨论）
- **GPU 加速 / OpenGL / 矢量字体**。（可讨论）
- **自研真 C/C++ 编译器**（能编译任意子集源码，而不是脚本解释器）：这是比第七阶段还大的独立工程，只有前面全部落地、且脚本阶段证明"自研语言层"这条路走得通之后才值得开。（可讨论）

## 12. 风险与"开工前必须先定"的决策

| 风险 / 决策点 | 何时必须定 | 建议 |
|---|---|---|
| 用户镜像格式（MYOS 头 + `user_layout()`，装载地址 0x40000000） | 第一阶段 1b 开工前 | 复用 `cofllink`，不要引入 ELF 解析（本机没有可用的 `ld` 产出裸机 ELF） |
| syscall ABI 冻结时机 | 1b 定 v1，第五阶段冻结 | 错误码用负值、调用号只增不改；`docs/abi.md` 是唯一权威 |
| myfs v2 与已有 v1 卷 | 第三阶段开工前 | 不做就地升级：新格式 + 重建测试卷；用户数据盘提供 `--rebuild` 并明确告知会清空 |
| `..` 怎么实现（父指针 vs 路径栈） | 第三阶段开工前 | v2 的目录 inode 里存父目录号（简单、可校验） |
| loader 448 KiB 上限 | 内核超过 400 KiB 时 | 方案 A：精简内核；方案 B：保护模式入口里用 ATA PIO 直接把剩余扇区读到 1 MiB（loader 只暂存引导必需的一小段）。先量再选 |
| 中断上下文里能做什么（能否阻塞、能否用缓冲缓存） | 第二阶段开工前 | **已定（2a）**：中断里只做记账和切换，绝不阻塞、绝不分配/释放堆内存（`task_reap()` 因此只能在任务上下文调用）；**EOI 必须在处理函数之前发**，因为处理函数会切换任务 |
| 每进程页目录的物理页开销 | 第二阶段（2a 已用 1 页/任务，页表共享） | `-m 64` 起步（2b 开工前做），`vm` 命令暴露页表占用，回归里加"创建 32 个任务后仍能分配" |
| 任务栈大小与溢出检测 | 2a 已定 | 8 KiB/任务 + 栈底 canary；canary 丢了就是一条自检 FAIL，而不是静默踩内存 |
| 内核 shell 与用户态 shell 并存 | 第三/五阶段 | 保留内核 shell 作为应急入口（调试用），用户态 shell 是主入口 |

## 13. 依赖关系一图

```
阶段0 现状（引导 + 32位内核 + myfs 读写）            ✔
   │
1a 分页/物理分配/堆/缺页 ──┐                          ✔
   │                      │
1b ring3 + TSS + syscall + usercopy + 用户镜像        ✔
   │
2a 任务 + 抢占式轮转调度 + 每任务页目录/内核栈        ✔  ← 现在在这里
   │
2b 用户进程 + fork(COW) + exec/wait + 信号 ──┬── 最小 tty（行规程）
   │                                          └── IPC：管道 / 共享内存  （2c）
   │
3  VFS + 每进程 fd/cwd + myfs v2 + 硬/软链接 + 跨设备 ── ramdisk 设备
   │
4  设备模型 + /dev + 正式 tty/作业控制 + 块缓存 + RTC/软定时器
   │
5  用户态 libc + 用户态 shell（重定向/管道/环境变量/PATH）
   │
6  脚本语言：词法/语法/求值 + 按内容分派执行 + 脚本示例
   │
7a TUI → 7b 帧缓冲(VBE) → 7c 窗口系统/事件分发 → 7d 合成器
```

每一层的验收都能独立跑（不需要后面的阶段就位），所以任何一步都可以停下来当交付点。
